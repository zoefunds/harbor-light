# Security model

Harborlight assumes candidate pages, manifests, snapshots, route indexes, framework inventories, and challenge documents are hostile input. All inputs are size-bounded, canonically serialized, origin-checked, delimiter-defused, and passed to models as data. Model output uses closed schemas; validators independently recompute consequential fields. Semantic text and structural features are derived from the exact fetched bytes, and `body_sha256` must equal `assessed_body_sha256`.

The owner cannot weaken mandatory protocol policies, omit a route from the fixed framework inventory, register one path under multiple identifiers, challenge their own voyage, shorten review below the minimum, or bypass a hold. New candidates invalidate prior results. Final sealing re-fetches current bytes after the review period.

The deployment verifier requires an expected deployed-source hash and protocol ID from protected repository configuration. It obtains the source independently from Studionet, recomputes live manifest and route hashes, and verifies both canonical notarization commitments. A configured address alone is insufficient.

Residual risks include correlated model/provider failures, personalized or regional content, unstable sites, upstream RPC compromise, and misleading claims that are consistently present in both baseline and candidate. The authoritative scope is deliberately narrower than the whole console: it is every static HTML release handler under `app/demo`, discovered by the build-time `next-release-route-scan` and published at `/.well-known/harborlight-inventory.json`. Adding another release handler changes the generated inventory commitment and makes an incomplete chart fail closed. A compromised build pipeline could still falsify that artifact, so repository protection and CI remain part of the trust boundary. Semantic inspection is not interactive functional testing: Harborlight verifies static links/forms and public claims, while JavaScript execution, form submission, authentication, and destination availability remain the responsibility of browser/API tests. Detected ambiguity or limit overflow results in uncertainty; the protocol does not claim to establish real-world truth.
